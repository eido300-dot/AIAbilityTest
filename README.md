# AIAbilityTest

> האם באמת אפשר ליצור תוכנה טובה ואיכותית בעזרת AI?

פרויקט ניסויי שמטרתו לבדוק את השאלה הזו בצורה מעשית: לא לפי הבטחות שיווקיות ולא לפי דמואים של חמש דקות, אלא על ידי בניית תוכנה אמיתית והערכה כנה של התוצאה.

## למה הפרויקט הזה קיים

יש הרבה הצהרות על מה AI יכול (וגם על מה הוא לא יכול) לעשות בפיתוח תוכנה. מעט מהן מגובות בניסוי מתועד. הריפו הזה הוא ניסיון לענות על השאלה בעזרת עבודה בפועל:

- האם AI מסוגל לקחת רעיון ולהגיע ממנו למוצר שעובד?
- האם הקוד שהוא כותב קריא, בטוח וניתן לתחזוקה, או רק "עובד על המחשב שלו"?
- כמה פיקוח, תיקונים והכוונה אנושית נדרשים בדרך?
- איפה AI מצטיין, ואיפה הוא נכשל שוב ושוב?

## עקרונות העבודה

1. **ה-AI כותב את הקוד.** האדם מגדיר דרישות, נותן משוב ומבצע בדיקות, ולא כותב את הקוד במקומו.
2. **שקיפות מלאה.** כל התערבות ידנית בקוד מתועדת, כדי שאפשר יהיה להבדיל בין מה שה-AI עשה לבין מה שהאדם תיקן.
3. **כישלונות נשארים בהיסטוריה.** ניסיונות כושלים, באגים וחזרות לאחור מתועדים ואינם נמחקים. הם חלק מהתשובה לשאלה.
4. **מדידה לפני מסקנות.** מסקנות מבוססות על קריטריונים שהוגדרו מראש (ראו להלן) ולא על תחושה.
5. **הפרומפטים מנוסחים בצוותא.** כל חברי הקבוצה לוקחים חלק בניסוח הפרומפטים, כך שהתוצאה משקפת את הצוות כולו ולא את סגנון הכתיבה של אדם אחד.
6. **הביקורת פתוחה לכולם.** כל אחד רשאי לבחון את הקוד, את הפרומפטים ואת ההערכות, ולהעיר עליהם. ביקורת היא חלק מהניסוי ולא איום עליו.

## איך נמדדת "איכות"

| קריטריון              | מה בודקים                                                  |
| --------------------- | ---------------------------------------------------------- |
| **נכונות**            | האם התוכנה עושה מה שהוגדר, ועוברת בדיקות אוטומטיות?        |
| **קריאות ותחזוקתיות** | האם אדם אחר יכול להבין ולשנות את הקוד? האם המבנה הגיוני?   |
| **אבטחה**             | האם יש חולשות מוכרות, טיפול לקוי בקלט או חשיפת סודות?      |
| **עמידות**            | טיפול בשגיאות, מקרי קצה ותנאים לא צפויים                   |
| **תיעוד ובדיקות**     | האם ה-AI מייצר גם תיעוד ובדיקות, ועד כמה הם שימושיים באמת? |
| **תהליך**             | כמה איטרציות, כמה זמן וכמה התערבות אנושית נדרשו?           |

## שיטת העבודה

1. **הגדרת המוצר**: מפרט ברור של מה נבנה, ומה נחשב "הצלחה".
2. **בנייה בעזרת AI**: הפיתוח נעשה בשיחה עם AI, בצעדים קטנים וניתנים לבדיקה. הפרומפטים מנוסחים יחד על ידי כל חברי הקבוצה.
3. **בדיקה והערכה**: הרצה, בדיקות אוטומטיות וסקירת קוד מול הקריטריונים שלמעלה. הביקורת פתוחה לכולם.
4. **תיעוד**: רישום של מה עבד, מה לא, ומה נדרש כדי לתקן.
5. **סיכום**: מסקנות כנות בסוף כל שלב.

## סטטוס

🚧 **תשתית פיתוח ראשונית.** המוצר שנבחר לניסוי הוא מערכת ניהול לקוחות כללית
למכירה לעסקים, עם סביבת עבודה מבודדת לכל עסק ומשתמשים פנימיים בלבד.
קיימים שלד ממשק ושרת, מסד פיתוח ובדיקות בידוד. עדיין אין הזדהות, ממשקי
לקוחות, תהליכי מכירה או חיוב. המערכת אינה מוכנה להפעלה מסחרית.

## מתחילים לעבוד

דרישות: Node.js לפי `.nvmrc`, npm מסדרה 11 ודוקר עם compose.

```bash
npm ci
npm run setup:local
npm run db:up
npm run db:migrate
npm run build
npm run dev
```

מסך הפיתוח בודק מוכנות אמיתית של השרת ובסיס הנתונים. הגדרות מקומיות
נוצרות עם סיסמאות אקראיות ונשמרות מחוץ למעקב. הוראות מלאות, יציאות,
בדיקות ופתרון תקלות ב־[מדריך הפיתוח](docs/development.md).

## מפת המאגר

| מקום                | תוכן                                   |
| ------------------- | -------------------------------------- |
| `apps/web`          | ריאקט וטייפסקריפט; מסך סטטוס בעברית    |
| `apps/api`          | נסט וטייפסקריפט; בדיקות זמינות ומוכנות |
| `packages/database` | פוסטגרס, גרסאות מבנה ובידוד עסקים      |
| `apps/worker`       | חוזה עתידי; אין עובד רקע פעיל          |
| `tests/e2e`         | בדיקות דפדפן מול השרת והמסד            |
| `.github/workflows` | הגדרת בדיקות אוטומטיות                 |
